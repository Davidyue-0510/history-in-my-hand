# 历史沙盘 · 架构纲要 v0.1

> 状态：设计讨论稿。基于三段需求口述整理，未开始实现。
> 日期：2026-08-06

---

## 0. 一句话定义

**这不是一个历史地图工具，而是一个「带出处与置信度的历史断言库」，地图、时间轴、人物关系网、赋税曲线都只是它的视图。**

判断依据：需求中最有分量的一句是"设置存放不同版本的史料，相互佐证或者攻击"。市面上所有历史地图产品（谭其骧图集、CHGIS、各类时间轴）呈现的都是**已被裁决过的单一结论**；本项目要呈现的是**裁决过程本身**。这是唯一的结构性差异点，也是护城河所在。

---

## 1. 数据内核：五个原语

只有五个概念是一等公民。任何新增维度都必须能被这五个表达，否则不予收录。

### 1.1 Source 史料
```
source_id, 书名, 卷/篇, 版本/刻本, 作者, 成书年代,
立场标签[官修/私修/敌方/第三方/当事人], 传抄谱系(引自哪本), 数字化出处
```
立场标签是后续冲突裁决的核心依据。朝鲜《栅中日录》之于萨尔浒，价值不在于它更准，而在于它是**第三方参战者**。

### 1.2 Assertion 断言（原子单位）
```
assertion_id,
主语(entity_id), 谓词(predicate), 宾语(值 或 entity_id),
时间效力(start, end, 精度, 原始纪年文本),
空间(place_id 或 geometry),
出处(source_id + 原文片段),
置信度(0-1 或 分级),
生成方式(原文直述 / 原文推断 / 学界考证 / AI 推演)   ← 关键字段
```

**「生成方式」字段是整个项目的生死线。** 一旦 AI 推测的兵力数字和《明实录》原文混进同一图层且不可区分，项目就从史料工具退化为精致的谣言机器，且不可逆。该字段必须在数据层、API 层、UI 层三重可见，AI 层默认可一键关闭。

### 1.3 Entity 实体
人物 / 地点 / 机构 / 军队 / 物产。**实体本身几乎没有属性**——所有属性都是带时间效力的断言。

### 1.4 Event 事件
共享时间、空间、参与者的一组断言的**捆绑视图**，不是独立存储层。
类型：战争 / 灾祸 / 行政调动 / 水利 / 科举 / 商贸 / 宗教 / 营建 / ……

### 1.5 State 状态截面 —— **计算得出，不落库**
```
State = fold(place, time, 采信的 source 集合, LOD 层级)
```
给定"广宁 · 万历四十七年三月 · 只信《明实录》"，折叠出一个状态向量（人口、驻军、粮储、税额、气候、主政者……）。

**State 是查询结果而非数据表**，这一条决定了多版本能不能做成。用户切换采信集合 →
同一时空的地图**当场改变**。这是本项目最有冲击力的演示，也是任何现有产品做不到的。

## 2. 关于「类继承 + Python 字典」的修正建议

原始想法是用类继承扩展地方数据库、用 dict 存储。方向对，但**继承用在实体实例上会崩**：

| 问题 | 例子 |
|---|---|
| 身份随时间变化 | 朱元璋：农民 → 僧 → 红巾军将领 → 吴国公 → 皇帝。类无法在运行时优雅改变 |
| 身份并发叠加 | 一人同时是 进士 + 同乡 + 东林党 + 兵部尚书，多重继承地狱 |
| 类别本身随时代变化 | 1400 年的"卫所"≠ 1600 年的"卫所" |

**替代方案：组合 + 时间效力（Entity–Component）**

```python
朱元璋 = Entity(id="P0001")
roles = [
    Role("红巾军将领", 1352, 1356, source=...),
    Role("吴国公",     1364, 1368, source=...),
    Role("皇帝",       1368, 1398, source=...),
]
```

继承仍然有用——但用在 **Schema/组件类型定义** 上（`战争事件` 继承 `事件`），不用在实体实例上。

**存储演进路径：**
- 阶段一（原型）：Python dict / dataclass，落盘 JSONL —— 便于人肉审查与 git diff
- 阶段二（可查询）：SQLite + JSON1 + FTS5，单文件可携带，全文检索原文片段
- 阶段三（空间/规模）：DuckDB 或 PostgreSQL + PostGIS
- 关系网：先用 `relations` 表 + networkx 即可支撑很久，不要过早上 Neo4j

## 3. 地理是实体，不是底图

需求里"黄河在不同时期的改道"这一句，改变了地图层的架构。

常规 GIS 把地理当静态底图，本项目**每一个地理要素都自带时间效力**：

- 黄河河道：1194–1494 夺淮 / 1494–1855 / 1855–今
- 行政区划边界：随年份切片
- 海岸线、湖泊（如洞庭、鄱阳、云梦）、长城线、驿路网

所以"地图"= **时间参数化的图层栈**，`render(t)` 而非 `render()`。

**可复用的开源资产（第一优先级验证）：**
- **CHGIS** 中国历史地理信息系统（哈佛 + 复旦）—— 历史地名与政区
- **CBDB** 中国历代人物传记资料库（哈佛 + 北大 + 中研院）—— 人物、亲属、社会关系、任官
- **中国哲学书电子化计划 / 殆知阁** —— 古籍原文
- 历法换算：`sxtwl`（寿星天文历）等库处理年号—农历—公历

这三件东西决定项目能不能启动，建议在写任何业务代码前先跑通。

## 4. 维度无限增长的治理策略

需求列出了气候、土壤、地质、地形、植被、作物、水文、政区、驻军、税收、人口、民族、信仰、教育、经济、产业、科技、耕地、粮储、衣料、柴米油盐酱醋茶、居住形式……并注明"可以一直补充"。

**如果这些都做成一等 schema 字段，项目会死于 schema 变更。**

策略：**冻结的小内核 + 开放的受控词表**

- 内核：第 1 节的五个原语，**永不扩展**
- 维度：全部表达为 `predicate`（谓词），登记在一张可增长的词表里
- 每个谓词声明：单位、值域、典型史料来源类型、所属 LOD 层级、是否可插值

> "有哪些信息，可参考地方博物馆展览包含的栏目" —— 这个想法非常好，建议直接采用为**词表的初始来源**。博物馆策展人已经替我们解决了"用哪些维度描述一个地方和一个时代"这个问题，且经过公众验证。

## 5. LOD：分的不是精度，是信息性质

原始表述是"为了释放运存"。这低估了这个设计本身。

三层展示的不是"更多细节"，而是**性质不同的信息**：

| 层级 | 看的是 | 内容 |
|---|---|---|
| 文明 / 天下 | **势** | 疆域边界、政权更迭、气候期、大事件 |
| 省 / 布政使司 | **人与线** | 省级大事、进攻路线、科举与派系、主要人物关系 |
| 县 / 州府 | **血肉** | 县志、详细战况、死亡与俘获、灾荒、赋役 |

这已经不是缩放，是**三种史观**。

实现要点：每条断言在入库时打上 `scale` 标签，LOD 切换是**数据库过滤**而非渲染层裁剪。

**「影响力」指标**（需求原文：由影响区域范围决定）值得单独打磨，建议为多因子：
`影响力 = f(影响地理范围, 影响人口, 持续时长, 被史料提及频次, 关系网中心性)`

## 6. 正向与反向：同一个状态向量的两个方向

这是本轮最重要的结构性发现，修正了此前"应做成两个产品"的判断。

需求中有一句旁白：**"突然有种感觉，掌握了这些信息，之后会安定还是战乱，一点不意外。"**

这句话就是整个项目的理论内核——**一个地方的状态向量（气候、收成、赋税、驻军、人口、教育、信仰）在很大程度上预示了它的事件走向**。

于是正向与反向共用同一套 State schema，只在**因果层**分岔：

```
正向（复原）:  史料 → 断言 → State(t)          【刻意不含 WHY】
反向（演化）:  State(t) + 决策规则 → 新断言 → State(t+1)   【全部是 WHY】
```

需求明确说"五个 W 中的四个"，主动排除了 WHY。这个取舍是对的：**WHY 是解释不是数据**。而反向引擎恰恰完全建立在 WHY 之上——人物性格、关系、利益如何驱动决策。

**这带来一个额外好处：** 反向生成的内容天然流经同一个 `生成方式` 字段（值为 `推演`），第 1.2 节要求的隔离**自动成立**，不需要额外机制。

因此：**先把 State schema 做对，反向模式只是把"断言生产者"从史料换成推演引擎。**

## 8. 建议的第一个垂直切片

铺开做一百个事件，不如把一个做透。两个候选，性质不同：

### 候选 A：萨尔浒之战（1619）—— 事件切片
- 明军四路分进，天然适合地图叙事
- 明、后金、朝鲜三方均有一手记载且互相矛盾
- 兵力记载从十一万到四十七万都有说法
- **一个案例同时演示：行军轨迹 + 将领 + 版本冲突 + AI 补全**

### 候选 B：某一府县百年剖面 —— 地点切片
- 更贴近"县志数据库"和"安定还是战乱"这条主线
- 演示 State 状态向量随时间演化，气候—收成—赋税—民变的链条
- 更能验证反向引擎的可行性

建议顺序：**A 先做（冲击力强、易演示），B 紧随（验证理论内核）**。
