---

## 0. 结论先行

**你几乎不需要向任何单位申请权限。** 这个项目从一个 GitHub 仓库就能启动，不需要机构背书、不需要立项、不需要资质。

但有三件事必须尽早定，因为它们**一旦定错，后期迁移成本极高**：

1. 许可证（代码 + 数据分开定）
2. 第三方数据的引入方式（**这里有一个真实的法律陷阱**）
3. 「模拟校验」的定义（**这里有一个方法论陷阱，比法律陷阱更危险**）

## 1. 数据授权：一个必须提前避开的陷阱

我核查了纲要里推荐的两个核心数据源，结果比预期严峻。

### 1.1 CBDB（中国历代人物传记资料库）

- **学术分支许可：CC BY-NC-SA 4.0**（署名 - 非商业性 - 相同方式共享）
- 存在**商业分支**（由合作方 inindex.com 运营），学术分支的新增数据约**滞后商业分支一年**
- 数据量：约 649,533 人（2025-05），其中**明代 184,793 人**
- 下载：Harvard Dataverse / GitHub `cbdb-project/cbdb_sqlite`（SQLite 版）

**约束：NC 条款与本项目的商业化计划（剧本生成、沙盘可视化）直接冲突。**

### 1.2 CHGIS（中国历史地理信息系统）

情况更严格。V6 官方授权原文：

> License: free for academic research, **no commercial use, resale, or redistribution permitted.**

复旦方中文版权声明第 7 条：

> 没有管理委员会的书面协议表达的同意，无论修改与否，你不得把 CHGIS 数据整体包括在你自己的成果中……不得以任何电子载体形式或通过因特网下载的方式**重新发布** CHGIS 数据。

**这意味着：一个开源仓库不能把 CHGIS 数据打包进去。** 这不是 NC 的问题，是**禁止再分发**——对开源项目而言是硬阻断。

### 1.3 解法：适配器架构

**核心仓库不携带任何第三方数据，只携带下载脚本与转换适配器。**

```
repo/
  adapters/
    cbdb_adapter.py      # 用户本地下载 CBDB → 转换为本项目断言格式
    chgis_adapter.py     # 同上，数据不入库、不上传、不分发
    ctext_adapter.py
  data/
    core/                # 只放公有领域 + 社群自建数据，CC BY 4.0
```

这是机器学习项目的通行做法（不分发数据集，只提供 download script），法律上干净，且**用户体验几乎不受影响**——首次运行时跑一次拉取脚本即可。

### 1.4 真正开放、可直接分发的数据源

| 数据源 | 内容 | 许可 |
|---|---|---|
| World Historical Gazetteer | 历史地名（含部分 CHGIS 衍生层） | CC BY 4.0 |
| GeoNames | 现代地名 | CC BY 4.0 |
| Natural Earth | 底图、海岸线、河流 | 公有领域 |
| OpenStreetMap | 现代地理要素 | ODbL |
| ctext 中国哲学书电子化计划 | 古籍原文 | API，需免费注册 key |
| 古籍白文 | 超过保护期 | 公有领域 |

### 1.5 古籍版权的边界（重要）

- **古籍原文（白文）**：作者去世远超保护期，**公有领域，随便用**
- **点校本 / 校勘本**（如中华书局二十四史点校本）：中国大陆有判例倾向于认定**点校成果具有独创性、受著作权保护**。不要直接爬取或分发
- **今人译注、白话本、学术专著**：全部有版权
- **中研院史语所《明实录》校勘本**：校勘成果有权利主张，需留意

**安全路径**：使用公有领域影印本 / 白文数字化文本，或社群自行录入。这恰好也是「全民参与」的天然切入点——**录入本身就是贡献**。

### 1.6 因此：自建地名库是必需，也是价值

既然 CHGIS 不能再分发，项目**迟早要自建一套 CC0 / CC BY 的历史地名与政区库**。

这看似是负担，实则是本项目最硬的资产之一，而且与「全栈开放」的理念完全自洽：**世界上还没有一套真正自由许可、可商用、社群维护的中国历史地名库。**

## 2. 「模拟校验」：一个必须修正的设计

原始表述：

> 对于他们提供的数据资料的真假，会先代入模拟校验以后再更新。

**这个设计如果按字面实现，会毁掉项目的学术合法性。**

### 2.1 为什么危险

用模型来判定史料真假，是**循环论证**：

```
模型由已有史料训练/构建
  → 新史料与模型不符 → 判定为假 → 不入库
  → 模型永远自洽 → 模型偏见被固化为「历史事实」
```

后果是：**所有反常的、颠覆性的、孤证的记载会被系统性排除**。而历史学上最重要的发现，往往恰恰来自反常的孤证（甲骨文、敦煌遗书、明清档案，最初都是"不合常理"的）。

一个会自动删除异常值的历史数据库，比没有数据库更糟。

### 2.2 修正方案：三道门，且没有一道判真假

**门一 · 形式门（机器，自动，秒级）**
只检查**可机检的形式问题**，不涉及内容真伪：
- 时间能否落到历法基准（年号/干支 → 可解析）
- 地点能否落到地名库（或标记为待消歧）
- 引证是否可定位（书名 + 卷次 + 原文片段）
- 数值单位是否合法（石/斗/亩/丁/口）
- 是否与自身矛盾（卒年早于生年）

不通过 → 打回补全，**不判真假**。

**门二 · 冲突门（机器，自动）**
与既有断言矛盾时——**不拒绝，而是立此存照**：
- 自动生成一个「冲突对」
- 两条断言并存，各自保留出处与置信度
- 在 UI 上呈现为可切换的分歧点

这正是需求原文说的"单纯就是展示不同版本互相冲突的史料"。**冲突不是错误，冲突是产品**。

**门三 · 评议门（人 + 机器辅助，异步）**
可信度不是布尔值，是一个综合分：
```
置信度 = f(出处等级, 史料立场, 传抄谱系距离, 编者声誉, 同行复核数, 旁证数量)
```
低分不删除，只是**默认图层不显示**，可手动开启。

### 2.3 那模拟到底用来干什么？

模拟**不做裁决，只做提示**。

例：某县上报人口在三年内下降八成，而同期没有任何战乱、灾荒、疫病、析置记载。系统不判定这条数据为假，而是挂一个标记：

> ⚠ 异常：此处人口断崖，但无对应事件记载。可能原因：录入错误 / 单位歧义（丁 vs 口）/ 史料缺失 / 存在未被记录的事件。

**这是"提出问题"，不是"给出判决"。** 而且它恰好指向你那句旁白——真正有价值的不是模拟能验证什么，而是**模拟失配的地方，往往就是史料缺环所在**。这可以变成项目的一个特色功能：**自动生成"史料缺口清单"，引导社群去补**。

## 3. 「全栈开放 + 商业化」如何共存

这两者不矛盾，但需要结构设计。

### 3.1 许可证建议

| 部分 | 建议许可 | 理由 |
|---|---|---|
| 代码 | **AGPL-3.0 + CLA** | AGPL 防止他人闭源 SaaS 套壳；CLA（贡献者许可协议）保留你另行商业授权的权利。GitLab / MongoDB 走的就是这条路 |
| 核心数据 | **CC BY 4.0** | 只要求署名，允许商用。有利于传播，也不阻碍你自己商用 |
| 第三方数据 | 不分发，适配器加载 | 见 1.3 |
| AI 推演内容 | CC BY 4.0，但**强制标注来源为推演** | 见纲要 §1.2 |

**注意**：如果核心数据选 CC BY-**SA**（相同方式共享），你自己基于数据做的商业剧本可能也被要求开源。**建议用 CC BY 4.0，不要 SA。**

### 3.2 关于 CLA 的现实建议

CLA 会**劝退一部分开源贡献者**（他们不愿意把权利让渡给个人/公司）。折中方案：
- 用 **DCO**（开发者原创声明）替代 CLA，门槛低得多
- 商业化不靠代码闭源，靠**托管服务 + 数据加工服务 + 定制沙盘**
- 这是更健康、也更容易吸引贡献者的路径

我倾向后者：**代码 AGPL + DCO，商业化卖服务不卖软件。**

## 4. 关于「我的角色是 idea 提出者」

需要诚实地说一件事，也需要给一个更准确的定位。

**诚实的部分**：在开源世界里，idea 是最不稀缺的东西。GitHub 上躺着无数个 star 数很高、README 写得极好、但一行代码没有的"愿景仓库"。历史可视化这个方向，过去二十年至少有几十个项目启动过，绝大多数死在第二年。

**但你的 idea 里有两样东西是真的稀缺的**：

1. **把版本冲突当成产品而不是缺陷** —— 这个视角我没在任何同类产品里见过
2. **正反双向共用一套状态向量** —— 这让它同时是学术工具和创作工具，两个市场

**更准确的角色定位**：不是"提出者"，是**守门人**。

开源项目最缺的从来不是写代码的人，是那个**始终在场、能说"这个不做"的人**。这个项目的维度可以无限扩张（你自己写了"可以一直补充"），一旦没人守住边界，它会在两年内变成一个谁也用不动的怪物。

守门人要做的事，恰恰不需要写代码：
- 决定什么进内核，什么只能当插件
- 决定一个争议怎么呈现
- 决定 demo 讲什么故事
- 拒绝 80% 的"好建议"

**这件事 AI 替不了你**，因为它需要品味和取舍，而不是知识。代码我可以写，取舍你来做。
